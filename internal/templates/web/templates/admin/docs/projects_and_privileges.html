Projects are the unit of OAuth client ownership and user access. Every project lives inside an organisation, holds its own privilege ladder, and has its own set of OAuth clients.

Projects can also issue signed licences independently of OAuth. Open a project and select Licences; see Project Licences for the security and operations model.

Privilege levels

Each project ships with five default rungs:

LevelDefault nameConvention
1OwnerProject lifecycle decisions; the legacy super-admin signal.
2AdministratorFull operations within the project.
3EditorRoutine writes.
4MemberRead + limited write.
5ViewerRead-only.

You can rename rungs, add more, or delete unused ones. Lower numbers always carry more privilege than higher numbers.

Assignments

An assignment binds one user to one project at one privilege level. A user without an assignment cannot complete an OAuth flow against any client in that project — even if their credential is valid, the authorise endpoint returns access_denied.

How privilege flows into tokens
  • Access tokens (JWT type) carry privilege_level and privilege_name claims.
  • Opaque access tokens carry the same fields in the database row; /oauth/introspect exposes them.
  • Downstream applications should authorise their own actions on the basis of these claims rather than blanket trust.
Approval gates

Operators don't have assignment_mutations_direct, so creating, updating, or removing assignments creates an approval request that another super-admin or operator with that capability must decide. The approval payload contains the full proposed change so reviewers can see exactly what was requested.
