By default BlackWall stores its JWT signing key as an RSA private key in the jwt_signing_keys table. That's fine for development and most single-operator deployments, but it's a SOC 2 / FedRAMP / HIPAA finding waiting to happen: an attacker with database access can mint tokens that say anything.

The Signer interface in internal/service/signer.go abstracts the signing operation so the private key can live outside the process — in AWS KMS, GCP KMS, HashiCorp Vault, or any HSM with a SIGN/VERIFY profile.

The interface
type Signer interface {
    KeyID() string
    Algorithm() string                  // "RS256"
    PublicKey() *rsa.PublicKey          // for JWKS export
    Sign(data []byte) ([]byte, error)
    Verify(data, sig []byte) error
}

Today's implementations:

  • LocalDBSigner — the existing path. Private key materialised into the process at boot.
  • kmsSignerStub — placeholder that fails loudly if the operator selects a cloud backend in config but the matching build tag wasn't enabled. Misconfigured deployments crash at the first token mint rather than silently falling back.
Adding a real backend

The pattern for each cloud is intentionally similar — the signer just dispatches the SHA-256 digest of data and returns the cloud's signature bytes. Live behind a build tag so the cloud SDK only inflates the binary for operators who actually need it.

AWS KMS
  1. Create a KMS key with KeySpec=RSA_2048, KeyUsage=SIGN_VERIFY.
  2. Implement internal/service/signer_aws.go behind //go:build kms_aws:
    • Sign: call kms.Sign with SigningAlgorithm=RSASSA_PKCS1_V1_5_SHA_256, MessageType=DIGEST, sending the local SHA-256 of data.
    • PublicKey: fetch kms.GetPublicKey once at boot and cache.
    • KeyID: the KMS key ARN or alias.
  3. Build with go build -tags kms_aws ./cmd/blackwall.
GCP KMS

Same shape, behind //go:build kms_gcp. Use cloudkms.AsymmetricSign with RSA_SIGN_PKCS1_2048_SHA256.

HashiCorp Vault Transit

Behind //go:build kms_vault. Use the Transit engine's sign endpoint with signature_algorithm=pkcs1v15 and hash_algorithm=sha2-256.

What ALSO moves with the signer

Because the audit chain checkpoint signature goes through the same JWTManager.SignBytes, switching JWT signing to KMS automatically moves checkpoint signing to KMS too. SAML metadata + assertion signing similarly use the JWT key, so the entire signing posture migrates together.

Key rotation

KMS backends version their keys natively (AWS schedules rotation, GCP versions explicitly, Vault has a rotate operation). Today BlackWall's JWKS endpoint reflects whatever the active jwt_signing_keys rows say — when you move to KMS, the KMS-backed signer should publish its current public key version into a row so the JWKS endpoint sees it. Plan to advertise both the previous and the current public keys during the overlap window so in-flight tokens continue to verify.

What stays in-process even with KMS
  • Token verification is still done locally via the cached public key — KMS round-trips per verify would be cost-prohibitive at production traffic.
  • Session cookies, CSRF, and the audit chain row hashing all use symmetric crypto unrelated to the signing key.
