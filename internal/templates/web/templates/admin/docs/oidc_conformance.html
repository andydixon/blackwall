This page tracks where BlackWall sits relative to the OpenID Foundation's conformance suite, what's already covered, and which gaps remain before a Basic OP / OP+PKCE certification submission.

Why certification matters

The OpenID Foundation publishes a self-hosted conformance test suite at conformance.openid.net. Passing the relevant profile and submitting the results earns the right to use the "OpenID Certified" mark — a meaningful signal in enterprise security questionnaires and a prerequisite for some procurement processes.

Profile we target

Basic OP + PKCE. This is the response_type=code + S256 PKCE profile, which is what every modern SP uses. The full FAPI / Financial profiles are out of scope for the foreseeable future.

What's covered today
  • Discovery doc at /.well-known/openid-configuration — emits issuer, all endpoint URLs, supported response_types, grant_types, subject_types, signing algs, scopes, token endpoint auth methods, code_challenge_methods, claims, claim_types, and explicit false values for unsupported features (claims_parameter, request_parameter, request_uri_parameter). Also advertises supported prompt and display values plus service documentation URIs.
  • JWKS at /oauth/jwks — RSA public keys with stable kid.
  • response_type=code with mandatory PKCE S256.
  • nonce required on OIDC requests, echoed in the ID token.
  • at_hash emitted in the ID token, computed per spec (leftmost half of SHA-256 of access token).
  • state round-tripped through the redirect.
  • Error responses redirected to the redirect_uri with error + error_description + state.
  • prompt=none returns login_required when the user isn't authenticated, rather than rendering a login page.
  • prompt=login forces a fresh WebAuthn authentication regardless of session state.
  • Reserved claim protection — custom claims can never override iss, sub, aud, exp, iat, nbf, jti, nonce, at_hash, etc., even if an operator tries to set them.
  • userinfo endpoint verifies openid scope and bearer-token freshness (revocation, expiry, audience).
  • Token revocation at /oauth/revoke and introspection at /oauth/introspect.
  • Confidential and public clients — confidential clients authenticate via client_secret_post or client_secret_basic; public clients via none + PKCE.
Known gaps before submission
  • id_token_hint evaluation. When prompt=none arrives with id_token_hint, we should verify the hint is parseable, was issued by us, and the sub matches the current session. Today we honour prompt=none but don't cross-check id_token_hint. Fix is local to OAuthHandler.Authorize.
  • max_age evaluation. If the request includes max_age=N and the session's auth_time is older than N seconds, force a fresh WebAuthn authentication. We track auth_time in the JWT but don't enforce max_age at the authorize endpoint yet.
  • acr_values. Spec says if the SP requests an ACR we support, we should echo it in the acr claim. We don't emit an acr claim at all. Single-class deployments can fix this by always emitting "urn:oasis:names:tc:SAML:2.0:ac:classes:PasswordProtectedTransport"; richer step-up flows can map ACR values to required authenticators.
  • request and request_uri parameters. Currently disabled in the discovery doc, which is conformant — but a future profile may require either. PAR (Pushed Authorization Requests, RFC 9126) is the right modernisation.
  • response_mode=form_post. Advertised in discovery, but not implemented in Authorize's code-issuance path. Today we always redirect; the suite will exercise form_post and need an HTML form response.
  • End-session endpoint for RP-initiated logout. Not implemented. Spec calls for an end_session_endpoint in discovery (currently omitted, which is also valid — but enterprise SPs increasingly expect it).
  • Backchannel logout. Not implemented. Pairs naturally with the existing webhook infrastructure.
  • Signed userinfo. We always return userinfo as JSON. Advertising signed userinfo lets SPs verify integrity end-to-end; not in the basic conformance profile though.
Running the suite locally
  1. Clone the OpenID Foundation conformance suite: git clone https://gitlab.com/openid/conformance-suite.git. Build with ./run-tests.sh per its README.
  2. Create a confidential OAuth client in BlackWall via the admin UI or Terraform:
    • Grants: authorization_code, refresh_token
    • Redirect URIs: the suite gives you a callback URL when you start a test plan.
    • Scopes: openid profile email offline_access
    • OIDC enabled: yes
    • Access token type: jwt
  3. In the suite UI, configure the test plan with:
    • Discovery URL: https://<your-blackwall>/.well-known/openid-configuration
    • Client ID and client_secret from above
    • PKCE method: S256
  4. Run the Basic Certification Profile test plan first. Each failing test points at a specific OIDC clause to fix.
  5. Once green, re-run the OP+PKCE profile. Address remaining failures, repeat.
  6. Submit the green test log to the OpenID Foundation for certification per openid.net/certification.
Audit log signal

Every conformance suite request shows up in the audit log under oauth.authorize.begin, oauth.token.exchange, oauth.token.refresh, or oidc.userinfo.success — useful when you're debugging which specific test the suite is failing on.
