By default, BlackWall sessions are encrypted cookies — fast, scalable, but invisible to the server until they expire naturally. When a project enables db_sessions_enabled, each login additionally writes a user_sessions row that:

  • can be listed (admin sees every active session for a user),
  • can be revoked instantly (the next request that presents that cookie is rejected),
  • counts against a per-user cap (max_concurrent_sessions).
Where to manage them
  • Admin view: /admin/users/{uuid}/sessions — see, revoke one, or revoke all sessions for a user. Requires manage_users.
  • End-user view: the portal at /portal shows the user's own active sessions (coming in the next portal pass).
Concurrent-session cap

When the cap is set to N > 0, a fresh login that would push the user above N revokes the oldest active session first. The user on the oldest session is signed out at their next request. Useful for licence-style "single active device" controls.

What revocation actually does
  1. The user_sessions row's revoked_at is set to NOW.
  2. On the user's next request, the auth middleware looks up the row and refuses the request because it's revoked.
  3. The session cookie remains in the user's browser until it naturally expires (per the cookie's MaxAge), but it carries no authority.
What revocation does NOT do
  • It does not kill OAuth tokens issued during that session — those have their own oauth_access_tokens + oauth_refresh_tokens rows and lifecycles. To kill those, revoke the access/refresh tokens via the OAuth UI.
  • It does not log the user out of other projects unless you revoke their sessions there too.
Forced sign-out everywhere

The Revoke all button on the per-user sessions page kills every active session for that user across all projects. Use it after a credential delete, a status change to disabled, or any other action that should require re-authentication.
