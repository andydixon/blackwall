BlackWall ships a set of background jobs that prune expired material, plus the standard expectations around backup / restore.

Background jobs
JobWhat it cleans
cleanup_expired_codesAuthorisation codes past their expiry — they're already single-use, but rows pile up.
cleanup_expired_tokensAccess & refresh tokens whose expires_at has passed.
cleanup_revoked_tokensTokens revoked more than 24h ago.
cleanup_expired_challengesStale WebAuthn / portal challenge sessions.
cleanup_expired_rate_limitsOld rows in rate_limits past their window.
cleanup_audit_retentionAudit rows older than audit_retention_days. Set to 0 to disable.
cleanup_expired_approvalsApproval requests pending longer than approval_pending_max_age_days.
cleanup_expired_cryptbinCryptBin items past their expires_at; deletes the on-disk blob and metadata.
Triggering manually

Super-admins can run all jobs from /admin/maintenance. The button kicks off a background goroutine; refresh after a few seconds to see the run results.

Backup expectations
  • MySQL — full nightly dump plus binlog shipping to a separate host. The schema includes the JWT signing keys, so a database loss without backup means every issued token becomes unverifiable.
  • CryptBin storage path — back up to the same RPO as the database. Lose the blobs, lose the items: the database carries only metadata.
  • config.yaml — back up. Without the original session_secret, csrf_secret, cryptbin_kek_base64, and error_trace_key, you cannot read existing sessions, validate existing CSRF tokens, decrypt CryptBin DEKs, or decode error traces.
Recovery rehearsal

Twice yearly: restore the database + CryptBin storage path + config to a clean host, then attempt to (a) sign in as an existing user, (b) read an existing CryptBin item, and (c) verify an existing token via /oauth/introspect. If any of those fail, your backup set is incomplete.
