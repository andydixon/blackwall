BlackWall's audit log is hash-chained per row: every audit_log entry stores chain_hash = SHA-256(prev_hash || canonical_payload). That makes it impossible to alter an old row without invalidating every later row's hash. What chain_hash alone doesn't catch is wholesale truncation or replacement of the entire table; an attacker who can replay a clean snapshot can avoid hash drift.

Audit chain checkpoints close that gap. A periodic job records the tip of the log as a signed triple (last_audit_id, row_count, last_chain_hash), signed with the platform's active JWT key. Once published outside the database (S3 with versioning, a transparency log, your SIEM), any silent rewrite between checkpoints becomes detectable.

Where to manage them
  • Super-admin only: open /admin/audit/checkpoints or click Chain in the navbar.
  • Click Create checkpoint now to force a checkpoint outside the periodic schedule.
  • The Verify action recomputes the tip and confirms the signature is still valid under a known signing key. Drift surfaces as a structured failure message.
What verification proves
  1. Tip stability: the row at last_audit_id still has the recorded chain_hash.
  2. Row count stability: the number of rows up to and including the tip matches what we signed.
  3. Signature validity: the recorded signature still validates against an active or retired signing key. If the signing key has been rotated out completely, retain the old public key for verification.
Operational guidance
  • Run the checkpoint job at least daily; hourly is fine.
  • Ship checkpoints off-host immediately. A checkpoint in the same database it attests is only useful as a hint — an attacker with write access can manipulate both. Push to S3 (Object Lock + versioning), a transparency log, or your SIEM's WORM-style storage. Record the destination in exported_to.
  • If a verification fails, freeze further audit writes (operationally — there's no automatic switch yet) and investigate. The first bad row's ID gives you the boundary.
What the signature uses

The same RSA private key as JWT signing. Reuse is intentional: the audit chain shares a security boundary with token issuance, so a compromise that lets an attacker rewrite audit rows also gives them token-issuance capability anyway. When you move JWT signing to a cloud KMS (see KMS-pluggable signing), checkpoint signing follows automatically.
