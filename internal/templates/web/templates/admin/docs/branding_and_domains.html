Per-organisation branding lets the login surface carry the customer's logo, colour, and a supporting message — so users don't see a generic "BlackWall" page when signing into their own org's tools. Custom domains let the login URL itself live on the customer's domain.

Where to edit

Open /admin/organisations/{uuid}. Two cards:

  • Branding & login experience — logo URL, primary colour (hex), support email, and a multi-line login message.
  • Custom domains — register hostnames the customer wants to point at BlackWall.

Both require manage_organizations.

Branding fields
Logo URL
Absolute https URL the login template loads as an <img>. Host externally (S3, CDN); we don't host uploads.
Primary colour
#RRGGBB hex. Applied to primary buttons and the login card's accent line.
Login message
Up to 2 KiB of plain text shown above the WebAuthn prompt — use this for "Welcome to ACME corp" or compliance notices.
Support email
Rendered as a help link on the login card.
Custom domains

Mapping login.customer.com → BlackWall is a two-step process:

  1. DNS + TLS: the customer (or operator) configures DNS to point at BlackWall and provisions a TLS certificate for the host. BlackWall does not provision certificates itself.
  2. Map: add the hostname under Custom domains. It starts unverified. Click Verify once DNS resolution is confirmed.

Once verified, inbound requests with that Host header automatically pick up the org's branding overlay. The OIDC issuer URL is unchanged — only the login UI is rebranded.

Fallback behaviour

If a request arrives on a host that doesn't match any verified custom domain, the platform default branding is used. Existing organisations without any branding fields set are unaffected — they continue to render the default UI.

Gated by the project flag

Custom branding is only applied to projects whose custom_branding_enabled feature flag is on. New projects start with it on; pre-v3 projects start with it off. See Feature flags.
