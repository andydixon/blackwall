BlackWall acts as a SAML 2.0 Identity Provider for downstream SaaS apps that still speak SAML — half the enterprise SaaS catalogue. The flow reuses the existing WebAuthn login, so users never see a second authentication surface.

Per-project SP registry

Each project has its own list of registered Service Providers, managed at /admin/projects/{uuid}/saml. Requires view_projects to see, manage_projects to register.

IdP endpoints to share with the SP
Metadata URL
https://<your-blackwall>/saml/projects/{uuid}/metadata
SSO endpoint
https://<your-blackwall>/saml/projects/{uuid}/sso (both HTTP-Redirect and HTTP-POST bindings on the same URL)
Response binding
HTTP-POST to the SP's Assertion Consumer Service (ACS) URL.
Signature
RSA-SHA256, exclusive XML canonicalisation, signs both Response and embedded Assertion.
Registering an SP
  1. From the SP-side, obtain its Entity ID and ACS URL (sometimes called the "Consumer URL" or "Reply URL").
  2. In BlackWall, open the project's SAML page and click into the form at the bottom.
  3. Choose a NameID format — most apps want emailAddress. persistent is the right pick when the SP wants a stable opaque ID that doesn't change if the user's email changes.
  4. Fill in the Attribute map. Each line is saml_attr=source. Sources can be:
    • display_label — the user's primary label (typically their email).
    • Any custom OIDC claim name — pulls from the merged claim store, so org/project default claims feed straight into SAML attributes.
  5. Optional: paste the SP's signing certificate PEM to enforce signed AuthnRequests. Most major SaaS apps don't sign theirs, so this is usually blank.
SP-initiated flow
  1. Browser visits the SP. SP redirects to BlackWall's SSO endpoint with a SAMLRequest.
  2. BlackWall parses the AuthnRequest, looks up the SP by Entity ID, and stashes the request ID and ACS URL in the user's session.
  3. If not already logged in, the user is bounced through /portal/login for WebAuthn auth and returned here.
  4. BlackWall mints a signed Response containing a signed Assertion, then renders an auto-submitting HTML form that POSTs the Response to the SP's ACS URL.
Security properties
  • The AuthnRequest's AssertionConsumerServiceURL (when present) must match the registered ACS URL exactly. This prevents an attacker from making us POST our signed assertion to their server.
  • The Audience defaults to the SP's Entity ID, so the assertion can't be replayed against a different SP.
  • Subject confirmation has NotOnOrAfter = +5 minutes; Conditions has the same window.
  • Self-signed signing cert is generated from the active JWT key, so JWKS and SAML metadata advertise the same key identity. When you move JWT signing to a KMS (see KMS-pluggable signing), SAML signing follows.
What's intentionally not implemented
  • Single Logout (SLO) — out of scope until a customer needs it.
  • IdP-initiated SSO — every modern SP supports SP-initiated and the security model is cleaner.
  • Encrypted assertions — TLS already protects in transit and we don't have a use case where the receiving SP can decrypt-but-not-TLS-terminate.
  • HTTP-Artifact binding — vanishingly rare; not worth the complexity.
Audit

Every issued response logs as saml.response.issued with the SP entity_id, project, and actor user. SP registry mutations log as admin.saml.sp.create / admin.saml.sp.delete.
