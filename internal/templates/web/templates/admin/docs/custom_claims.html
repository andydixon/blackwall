BlackWall lets you attach arbitrary key/value pairs to a user that will be merged into every OIDC ID token and /oauth/userinfo response issued for them. Use this to surface organisation-specific attributes (department, cost-centre code, feature flags) to downstream applications without writing them into a custom directory.

Two scopes
  • User-level — set on the user, included in every token regardless of which project the token was issued for.
  • Project-scoped — set on a (user, project) pair, included only when the issued token is bound to that project. Lets different downstream applications see different per-user attributes without leaking across projects.

Project-scoped values override user-level values with the same key.

Where to set them

Open a user's detail page and click Custom claims, or navigate directly to /admin/users/{userUuid}/claims. The page shows one section for user-level claims and one section per project the user is assigned to. You can only see / edit project sections for projects in your admin scope.

Key rules
  • Keys must match [a-z][a-z0-9_]{0,79} — lowercase, digits, and underscore; first character a letter.
  • Reserved JWT and OIDC names are rejected at write time AND re-blocked at signing time: iss, sub, aud, exp, iat, nbf, jti, nonce, at_hash, c_hash, auth_time, acr, amr, azp, scope, client_id, token_type, expires_in, project_id.
  • Values are limited to 4 KiB.

Standards posture

Custom claims are emitted alongside the standard issuer-controlled claims; downstream OIDC libraries see them as ordinary additional claims, exactly as if they had been set by an external claims provider. The token remains a valid signed RS256 JWT and the discovery document is unchanged. at_hash still binds the ID token to the access token; nonce still echoes back; aud still names the requesting client.

Audit

Every claim mutation is logged under admin.claims.user.upsert, admin.claims.user.delete, admin.claims.project.upsert, or admin.claims.project.delete with actor, target user, project (where applicable), and the claim key. Reserved-key write attempts are logged with outcome=fail so abuse attempts surface in the dashboard.
