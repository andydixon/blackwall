BlackWall lets you attach arbitrary key/value pairs to a user that will be merged into every OIDC ID token and /oauth/userinfo response issued for them. Use this to surface organisation-specific attributes (department, cost-centre code, feature flags) to downstream applications without writing them into a custom directory.

Four layers

Claims are merged from the broadest to the narrowest layer; whenever two layers share a key, the later (narrower) layer wins:

  1. Organisation defaults — set on the organisation, applied to every user in the org regardless of project. Use this for values that should be the same for everyone in the tenant (e.g. tenant, support_url).
  2. Project defaults — set on the project, applied when the token is bound to that project. Use this for downstream apps that need the same claim across all users (e.g. a Grafana project assigning preferred_username = "team-grafana" or groups = ["editors","viewers"]).
  3. User-level — set on the user, included in every token regardless of project. Overrides org/project defaults for that one user.
  4. User × project — set on a (user, project) pair, included only when the token is bound to that project. The narrowest layer — wins over everything else.
Where to set them
  • Org defaults: Default OIDC claims card on the organisation detail page (/admin/organisations/{uuid}).
  • Project defaults: Default OIDC claims card on the project detail page (/admin/projects/{uuid}).
  • User-level and user × project: Custom claims from the user detail page (/admin/users/{uuid}/claims). Inherited org and project defaults show up read-only at the top so you can see exactly what the user is starting from.

You can only see and edit layers within your admin scope — an org admin can manage org/project defaults inside their org but not in another org.

Grafana example

To make the Grafana project hand preferred_username and a groups array to every user that logs in via the Grafana OAuth client:

  1. Open the Grafana project's detail page in /admin/projects.
  2. In Default OIDC claims add preferred_username = "team-grafana" (or the same as the user's email) and groups = ["editors","viewers"].
  3. Every user assigned to the project now receives those claims in /oauth/userinfo by default. Override for a specific user via their Custom claims page.
Key rules
  • Keys must match [a-z][a-z0-9_]{0,79} — lowercase, digits, and underscore; first character a letter.
  • Reserved JWT and OIDC names are rejected at write time AND re-blocked at signing time: iss, sub, aud, exp, iat, nbf, jti, nonce, at_hash, c_hash, auth_time, acr, amr, azp, scope, client_id, token_type, expires_in, project_id.
  • Values are limited to 4 KiB.

Standards posture

Custom claims are emitted alongside the standard issuer-controlled claims; downstream OIDC libraries see them as ordinary additional claims, exactly as if they had been set by an external claims provider. The token remains a valid signed RS256 JWT and the discovery document is unchanged. at_hash still binds the ID token to the access token; nonce still echoes back; aud still names the requesting client.

Audit

Every claim mutation is logged with actor, target, and the claim key:

  • User-level: admin.claims.user.upsert / admin.claims.user.delete
  • User × project: admin.claims.project.upsert / admin.claims.project.delete
  • Organisation defaults: admin.claims.org.upsert / admin.claims.org.delete
  • Project defaults: admin.claims.project_default.upsert / admin.claims.project_default.delete

Reserved-key write attempts are logged with outcome=fail so abuse attempts surface in the dashboard.
