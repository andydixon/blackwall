BlackWall's authorisation model has three layers:

  1. Admin role — one of super_admin, operator, or auditor. Each role grants a fixed set of named capabilities.
  2. Scope — for non-super-admins, the set of organisations and projects the actor can see and act on. Super-admins are scope-unbounded.
  3. Approval gates — capabilities ending in _direct let the actor mutate immediately; otherwise the change becomes an approval request.
Roles
RoleHeadline
super_adminUnrestricted scope, every capability, including direct status changes and credential deletes.
operatorDay-to-day administration scoped to organisations they own. Mutations route through approvals.
auditorRead-only: audit log, dashboard, scope debugger, error trace decoder, docs.

The complete capability list per role lives at Admin roles > Capability matrix.

Project licence inspection is granted by view_licences to super-administrators and scoped operators. The high-impact manage_licences capability, which signs and revokes licences, is super-administrator-only.

Scope

Scope is computed per-request from the user's organisation memberships:

  • If the user has the super_admin role or is a level-1 member of the legacy super-admin project, they see everything.
  • Otherwise, scope is the union of organisations where they are listed as admin_user_id, plus all projects belonging to those organisations.

Scope is enforced at every list query and at every per-resource detail/update handler. An out-of-scope project URL returns 403, not 404, so URL-guessing is a deliberate signal.

Approval gates

The following mutations route through the approval workflow when the actor lacks the matching _direct capability:

  • User status changes (change_user_status_direct)
  • WebAuthn credential deletions (delete_credentials_direct)
  • Project name and status changes (update_project_settings_direct, change_project_status_direct)
  • Privilege level deletions (delete_privilege_direct)
  • OAuth client settings and status changes (update_client_settings_direct, change_client_status_direct)
  • All assignment mutations (assignment_mutations_direct)

Request → review → decision is end-to-end audited; see Approvals Workflow.
