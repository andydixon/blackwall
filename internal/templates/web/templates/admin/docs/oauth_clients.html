OAuth clients are downstream applications that ask BlackWall to authenticate users. Every client is registered against exactly one project and inherits that project's user pool.

Client types
TypeWhen to chooseToken endpoint auth
Confidential Server-side applications that can keep a secret (Go services, PHP backends, server-side rendered apps). client_secret_basic or client_secret_post
Public Browser SPAs and native mobile/desktop apps that cannot keep a secret. none — security comes entirely from PKCE
Required parameters at /oauth/authorize
  • response_type=code — only the Authorisation Code flow is supported.
  • client_id — the public ID shown on the client detail page.
  • redirect_uri — must be one of the URIs registered on the client (exact match including scheme, host, port, path).
  • code_challenge + code_challenge_method=S256 — PKCE is mandatory for every client, public or confidential.
  • scope — space-separated; subset of the client's allow-list.
  • nonce — required when openid is in scope.
  • state — strongly recommended for CSRF protection on the redirect.
  • max_age — optional non-negative seconds. If the current authentication is older, BlackWall requires a fresh WebAuthn assertion. The resulting ID token carries the corresponding auth_time.
OIDC authentication freshness

OIDC enabled is an enforcement switch, not just a label: clients with it disabled cannot start new openid authorisation requests. For enabled clients, BlackWall records the successful WebAuthn time, signs it into auth_time, and preserves the same value when refresh tokens rotate. A relying party that sends max_age gets a new passkey prompt whenever that recorded authentication is too old. Disable the whole client or revoke its tokens as well if existing sessions must stop immediately.

Token type choice

JWT is the default. JWTs are signed RS256, include scope, project_id, privilege_level/name, and (for ID tokens) at_hash per OIDC §3.1.3.6. They are also stored as a hash in oauth_access_tokens so revocation works.

Opaque stores the random token in the database and forces every authenticated request through /oauth/introspect. Pick this if downstream services need real-time revocation visibility and don't mind the round-trip.

Refresh tokens

Issued only when the client requests offline_access. Each refresh is single-use: the old token is revoked and a new one returned. Re-using a refresh token triggers token family revocation — every active access and refresh token for that user/project/client triple is revoked, in line with current OAuth 2.1 best-practice.

Approval gates

Editing client name, redirect URIs, scopes, token lifetimes, or status all route through approval if the actor lacks update_client_settings_direct. The proposed and current settings are both included in the approval payload.

Client favicon on the authorisation screen

Blackwall requests /favicon.ico from the HTTPS hostname of the exact registered redirect URI used for the authorisation request. Only standard port 443 and public DNS addresses are eligible. DNS is resolved and pinned before connecting; private, loopback, link-local, reserved, IP-literal, redirected, oversized, SVG, and non-image responses are rejected. Successful icons are cached in memory for 24 hours and missing icons for 10 minutes. The client's initial remains as an inaccessible-site fallback.

Discovery

The OIDC discovery document at /.well-known/openid-configuration advertises response_types_supported=["code"], code_challenge_methods_supported=["S256"], and token_endpoint_auth_methods_supported=["client_secret_post", "client_secret_basic", "none"]. Clients that ignore this and try other flows will be rejected at /oauth/authorize.
